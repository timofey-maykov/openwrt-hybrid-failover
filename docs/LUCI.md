# LuCI: руководство пользователя

Веб-интерфейс **`luci-app-hybrid-failover`** настраивает Hybrid Failover на роутере без ручной правки UCI.

**Меню:** Сервисы → Hybrid Failover  
**URL:** `http://ROUTER/cgi-bin/luci/admin/services/hybrid-failover`

Нужен установленный **`hybrid-failover-core`** (бинарник `/usr/sbin/hybrid-failover`). LuCI обращается к нему через rpcd. Каждая кнопка вызывает ubus-метод `hybrid-failover.*`, а rpcd запускает `hybrid-failover rpc <Method>` и возвращает JSON.

Интерфейс написан на русском. Английский каталог переводов есть (`luci/po/en`), но он неполный, подробности в [luci/README.md](../luci/README.md).

---

## С чего начать

1. Установите пакеты по [INSTALL.md](INSTALL.md). Режим `full` ставит core, LuCI и бота. Скрипт установки сам выполняет `hybrid-failover migrate`, включает и запускает службу.
2. Откройте **Сервисы → Hybrid Failover**. Сразу откроется вкладка **Обзор**. Статус рядом с заголовком должен быть "В норме", а карточки Engine, nft / tproxy и Control должны показывать "работает" и OK.
3. Настройте **Маршрутизацию**: VPN или proxy, списки доменов.
4. Если нужно, добавьте правила на вкладке **Клиенты** (консоль, телевизор, телефон с другим режимом).

## Обзор

Страница только показывает состояние, конфиг здесь не редактируется. Данные обновляются каждые 5 секунд, рядом с кнопкой **Обновить** видно время последнего обновления и отсчёт до следующего. Селектор **Секция** в шапке выбирает, для какой секции маршрутизации показывать контроллер и каналы.

Рядом с заголовком стоит общий статус: "В норме", "Деградация", "Недоступно" или "Неизвестно". "Недоступно" значит, что не работает engine, nft или control plane. "Деградация" бывает, когда primary VPN упал и трафик идёт через резерв, когда не прошла проверка fakeip или когда core вернул ошибки. Там же версия core и режим engine (`native`).

Под заголовком большой блок со статусом, активным каналом и ссылками на Маршрутизацию, Диагностику и Клиентов. Ниже четыре внутренние вкладки.

**Обзор.** Карточки Engine, nft / tproxy, Control, fakeip DNS, Политика, Активный outbound и Резервы (сколько резервных каналов живо, например `2/3 живы`). Дальше карточки каналов failover и панели Маршрут, Контроллер и URLTest: selector, режим, primary probe, задержка primary, время последнего probe и последнего переключения, счётчики fail и recover, параметры urltest. Справа блок **Ручное переключение**.

**Каналы.** Таблица каналов: статус, канал, тип, задержка, тренд, роль. Тренд рисуется по истории задержек, которую core пишет в `/var/run/hybrid-failover/delay-history.json` (RPC `DelayHistory`, размер буфера задаёт опция "Точек delay-history на канал" на вкладке Маршрутизация). Если серверной истории нет, график строится по последним 40 замерам, которые браузер сохранил у себя.

**Журнал.** История переключений из `/var/log/hybrid-failover/history.jsonl`. Для каждого события видно время, секцию, переход, причину, политику и probe. Показываются последние 15 или 50 событий.

**Инструменты.** Кнопки **Live probe**, **global-check**, **check-fakeip**, **Экспорт журнала** (скачивает `failover-history.json`) и **Сбросить графики**. Последняя чистит только историю задержек в браузере, серверный файл остаётся. Здесь же повторяется блок ручного переключения.

**Live probe** запускается только по кнопке. Он заново проверяет все каналы, на слабых роутерах это заметная нагрузка, поэтому автообновление его не делает.

### Каналы AWG

Для primary-канала на WireGuard или AmneziaWG (`{section}-awg-out`) главным признаком служит handshake, HTTP-проверка идёт как дополнительная. Если handshake свежий, а HTTP urltest не прошёл, канал считается UP с пометкой `wireguard handshake OK`. Если handshake нет или он старше 3 минут, канал DOWN с причиной `no wireguard handshake` или `wireguard handshake stale (...)`. Эти причины приходят из core на английском.

### Ручное переключение

Выберите секцию и outbound и нажмите **Переключить**, после подтверждения selector секции закрепится на выбранном канале. При политике `fastest` переключение недоступно, канал выбирает urltest.

В режиме urltest HTTP-проверка сама выбирает участника группы. Карточка AWG может показывать UP по handshake, а трафик при этом всё равно пойдёт через резерв, пока selector стоит на URLTest. Ошибка "switch request timed out" на старых версиях лечится обновлением core до 1.7.35 или новее.

Если на странице ошибка или "Нет данных", проверьте `/etc/init.d/hybrid-failover status` и запустите global-check на вкладке **Диагностика**.

## Маршрутизация

Здесь задаётся, куда уходит трафик, попавший под правила Hybrid Failover: community-списки, свои домены и подсети, маршрут секции по умолчанию.

### Глобальные настройки

Здесь включается Hybrid Failover и задаются тип и адрес DNS, Bootstrap DNS, отключение QUIC и IPv6 на LAN, основная секция, интервал обновления списков, загрузка community-списков через proxy, Webhook URL, "Исключить IP из маршрутизации", интервал probe контроллера, размер журнала failover и буфера delay-history, Subscription URLs.

В форме остались поля "Путь cache sing-box", "Clash API listen", "Включить Yacd (Clash UI)" и связанные с ними. Они относятся к прежнему движку на sing-box, native engine их не читает.

### Секция маршрутизации (`config section`)

Имя секции произвольное (`main`, `glob` и т. п.). От него зависят теги outbound: `{section}-out`, `{section}-urltest-out`, `{section}-awg-out`.

| "Тип подключения" (`connection_type`) | Смысл |
|-------------------|--------|
| `vpn` | Основной путь через VPN-интерфейс (`interface`, например `awgch`). С флагом "VPN + резервные proxy" можно добавить резервы в `failover_proxy_links` |
| `proxy` | Только proxy: одна ссылка (`proxy_string`), Outbound JSON или группа URLTest (`urltest_proxy_links`) |
| `block` | Reject для доменов и подсетей этой секции |

**VPN + резервы.** Если VPN падает, трафик уходит на резервные URI из списка "Резервные URI". Порядок в списке задаёт приоритет, его можно менять кнопками **Вверх** и **Вниз**. Политика задаётся полем "Политика failover": `outage-only`, `prefer-primary` или `fastest`. Кнопка **Проверить URI** показывает, как core разобрал ссылку.

**Списки.** Community lists, свои домены (`user_domains`, `user_domains_text`) и подсети (`user_subnets`, `user_subnets_text`) определяют, какой трафик попадает в секцию.

### Как сохраняются изменения

Внизу страницы блок **Применение конфигурации**.

- **2. Проверить** сохраняет форму и вызывает `hybrid-failover rpc Validate`. Результат появляется в поле под кнопками.
- **3. Применить** становится активной только после успешной проверки. Она запускает `hybrid-failover apply`. Core собирает конфиг заново и перезапускает маршрутизацию, если что-то изменилось.
- **Сохранить и применить** в этом блоке сохраняет форму, проверяет её и при успехе сразу применяет.
- **Откатить pending** удаляет снимок `/etc/hybrid-failover/pending/pending.json`. Такой снимок создаёт бот или команда `hybrid-failover pending capture`. Сама страница его не создаёт, изменения формы и файл конфига кнопка не трогает.

Стандартные кнопки LuCI внизу страницы ("Сохранить", "Сохранить и применить") только сохраняют форму и через 2 секунды запускают проверку в фоне. Уведомление появится, если проверка не прошла.

Validate и apply работают с файлом `/etc/config/hybrid-failover`. Форма LuCI при сохранении кладёт изменения в список непринятых изменений (счётчик в шапке LuCI). В файл они попадают, когда вы применяете их через этот счётчик, после этого procd сам вызывает `hybrid-failover reload`.

Там же кнопки **Обновить community lists**, **Обновить подписки** и **Дублировать секцию...**. Дублирование сразу записывает копию секции в UCI (с `uci commit`) и перезагружает страницу.

Все опции UCI описаны в [UCI.md](UCI.md).

## Сервисы и каналы

![Вкладка «Сервисы и каналы»](img/luci-services.png)

Сверху карточки каналов каждой секции: состояние по urltest, задержка, открытые соединения, трафик и доля ожидаемой нагрузки от закрепленных списков. Карандаш рядом с названием переименовывает канал, название хранится в `channel_names` и привязано к серверу, а не к позиции ссылки.

Ниже таблица списков секции. Для каждого выбирается канал: пул (самый быстрый, как без привязки), конкретный канал, балансировка по всем, напрямую или блок. Колонка «Если канал упал» задает запасной путь. Колонка «Сейчас» показывает, куда список идет в эту минуту, например «канал упал, идет через пул».

**Распределить автоматически** раскладывает списки по живым каналам: тяжелые сервисы (видео) попадают на разные каналы, быстрые каналы получают больше. Результат можно поправить руками до сохранения. **+ Свой список** создает `user_list` с доменами и подсетями и сразу дает выбрать ему канал.

Изменения применяются кнопкой «Сохранить и применить», через обычное применение LuCI с откатом.

## Графики

![Вкладка «Графики»](img/luci-charts.png)

Живые графики по каждому каналу: входящий и исходящий трафик, открытые и новые соединения, задержка проверки с порогами 300 мс и 1 с и отметками отказов, доля трафика за период. Окно от 5 минут до суток, обновление от 2 до 30 секунд или пауза.

Выделите участок мышью, чтобы приблизить, двойной клик возвращает масштаб. Клик по каналу в легенде или по плитке оставляет на всех графиках только его, Ctrl/Cmd+клик скрывает или показывает канал. Наведение показывает значения всех каналов в этот момент на всех панелях сразу.

Данные пишет native engine раз в 2 секунды в `/var/run/hybrid-failover/channel-metrics.json` (последние 10 минут) и раз в минуту в `channel-metrics-24h.json` (сутки). Это tmpfs, после перезагрузки история начинается заново. Байты каналов на интерфейсе (VPN, AWG) берутся из счетчиков интерфейса, у прокси-каналов их считает engine.

## Клиенты

Здесь задаётся, какой LAN-клиент (по IP) участвует в Hybrid Failover и как именно.

### Два блока на странице

| Блок | Что это |
|------|---------|
| **Effective rules (как видит core)** | Только чтение: что core применяет сейчас (`list_clients`). Столбцы IP, Режим, Секция, Источник. Обновляется кнопкой **Обновить** |
| **Правила клиентов** | Редактируемые секции UCI `client_rule`: IP или CIDR, режим, секция маршрутизации для Full route |

Пустая таблица Effective rules чаще всего значит, что правил `client_rule` ещё нет, а не что core сломан. Страница подсказывает, что делать.

- "Нет правил клиентов. Добавьте client_rule ниже или выберите IP из DHCP." Core работает, добавьте правило.
- "Core не запущен. Запустите hybrid-failover, затем добавьте client_rule." Выполните `/etc/init.d/hybrid-failover start`.

### Режимы `client_rule`

| Режим | Когда использовать |
|-------|---------------------|
| **Include** | Клиент идёт через Hybrid Failover (nft mark и tproxy). Обычный выбор для устройства, которое должно пользоваться VPN или proxy роутера |
| **Exclude** | Клиент минует Hybrid Failover, трафик идёт напрямую |
| **Full route** | Весь трафик клиента идёт через выбранную секцию маршрутизации (поле "Секция маршрутизации", например `main`) |
| **Global exclude** | Клиент исключён из tproxy целиком, без правил отдельных секций |

Старые списки `settings.include_source_ips`, `exclude_source_ips` и `fully_routed_ips` core читает, только пока нет ни одной секции `client_rule`. Когда появилось первое правило, пользуйтесь только вкладкой **Клиенты**.

### Как добавить правило

1. Нажмите **Выбрать из DHCP...** и в таблице аренд нажмите **Выбрать** у нужного устройства. LuCI добавит строку правила и подставит IP. Можно и вручную, кнопкой **Добавить правило**.
2. Выберите **Режим**. Чтобы пустить устройство через Hybrid Failover, нужен **Include**.
3. Для **Full route** укажите секцию маршрутизации, её имя видно на вкладке Маршрутизация.
4. Нажмите **Сохранить и применить** или **Сохранить**. Обе кнопки сохраняют форму и сразу вызывают `hybrid-failover reload`, pending здесь нет. Как и на странице маршрутизации, в файл конфига изменения попадают после применения через счётчик непринятых изменений в шапке LuCI.
5. Нажмите **Обновить** в блоке Effective rules. Должна появиться строка с IP, режимом и источником `client_rule`.

### Выбор из DHCP

Кнопка **Выбрать из DHCP...** читает файлы аренд dnsmasq. Пути берутся из опций `leasefile` в `uci show dhcp`, а если их нет, из `/tmp/dhcp.leases`. Если там пусто, rpcd спрашивает odhcpd через `ubus call dhcp ipv4leases`. На обычном OpenWrt IPv4-адреса раздаёт dnsmasq.

Если список пуст:

- Проверьте `/tmp/dhcp.leases` на роутере.
- Убедитесь, что dnsmasq запущен.
- Посмотрите стандартную страницу LuCI **Статус → Обзор**, там аренды DHCP тоже должны быть видны.

## Диагностика

| Кнопка | Что проверяет |
|----------|----------------|
| **Validate** | UCI, URI в списках и сборку плана native engine без применения |
| **check-nft** | Таблицу nftables `inet hybrid_failover` |
| **check-fakeip** | DNS на `127.0.0.42` и fakeip |
| **global-check** | Сводный отчёт: engine, nft, fakeip. Результат показывается чеклистом, ниже есть Raw JSON |

Блок **Бэкап UCI** работает с архивом конфига.

- **Создать backup на роутере** пакует `/etc/config/hybrid-failover` в `/tmp/hybrid-failover-uci-backup.tar.gz`.
- **Скачать бэкап** отдаёт архив в браузер.
- **Восстановить** распаковывает архив по пути из поля под кнопками обратно в `/etc/config`.

Пригодится после смены конфига или когда с LAN вдруг ничего не открывается.

## Telegram

Вкладка настраивает бота (пакет `hybrid-failover-bot`). Страница состоит из четырёх частей.

**Сервис.** Поля из UCI `hybrid-failover-bot`. Это "Включить сервис" и пути к бинарнику, JSON-конфигу и лог-файлу. Они сохраняются обычными кнопками LuCI.

**Статус сервиса.** Состояние службы `hybrid-failover-bot` (running с PID или stopped) и кнопка **Обновить**.

**Hybrid Failover Bot: JSON-конфиг.** Форма для `/etc/hybrid-failover-bot.json`: токен, "Имя роутера (в уведомлениях и панели)", ID администраторов, ID только для чтения (`viewer_ids`), политика failover, URL Clash API, скрипт init.d, пути к логам, таймаут проверки, алерты failover (true/false) и их интервал в секундах. Пустое имя роутера означает hostname. URL Clash API нужен только старым установкам на sing-box. Список `routers` для управления несколькими роутерами в форме не редактируется, его правят в JSON вручную.

Кнопка **Сохранить в pending** по одному записывает поля через `hybrid-failover-bot -mode set-pending` в файл `/etc/hybrid-failover-bot.json.pending`. Рабочий конфиг при этом не меняется.

**Действия с конфигом:**

| Кнопка | Что делает |
|--------|------------|
| **Проверить pending** | `-mode validate-config`: проверяет pending-конфиг |
| **Применить** | `-mode apply-config`: проверяет pending, копирует его в `/etc/hybrid-failover-bot.json` и удаляет `.pending` |
| **Откатить** | `-mode rollback-config`: удаляет `.pending` |
| **Перезапустить бота** | `service restart hybrid-failover-bot` через ubus |

Бот читает конфиг только при старте, и **Применить** его не перезапускает. После применения нажмите **Перезапустить бота**, иначе он продолжит работать со старыми настройками.

Команды бота описаны в [bot/README.md](../bot/README.md).

## Когда изменения вступают в силу

| Страница | Что происходит |
|----------|------------|
| **Маршрутизация** | Проверить, затем Применить (`hybrid-failover apply`) или всё сразу кнопкой "Сохранить и применить" в блоке применения |
| **Клиенты** | Сохранение сразу вызывает `hybrid-failover reload` |
| **Telegram** | Свой pending-файл для конфига бота, после применения нужен перезапуск бота |

## Обновление

Кнопка **Проверить обновления** спрашивает у GitHub последний релиз. В таблице видно установленную версию, последнюю на GitHub и время проверки, а под ней список изменений. Если на GitHub версия новее, кнопка **Обновить** становится активной и показывает номер версии.

Обновление идёт в фоне. Роутер скачивает из релиза пакеты своей архитектуры, сверяет каждый файл с `manifest.json` по sha256 и размеру, ставит их через `apk` или `opkg`, выполняет `migrate` и перезапускает rpcd и службы. Страница сама следит за ходом, показывает шаг и журнал и перезагружается, когда всё готово. Настройки UCI не меняются. Бот и curfew обновляются, только если они уже установлены.

То же из консоли:

```sh
hybrid-failover update check     # что есть на GitHub
hybrid-failover update apply     # поставить последний релиз (в фоне)
hybrid-failover update status    # ход и журнал последнего обновления
```

`apply --foreground` ставит в текущей консоли, `--tag v1.7.48` берёт конкретный релиз, `--force` разрешает ту же или более старую версию.
